Analyzes Windows Office software for known CVEs using bulletin files, matching installed Office versions against security update records to detect unpatched vulnerabilities.

## Key Components

| Function | Description |
|---|---|
| `Analyze` | Main entry point — loads the latest bulletin, iterates installed Office software, detects vulnerabilities, and syncs results to the datastore |
| `getLatestBulletin` | Reads and deserializes the most recent `BulletinFile` from the vulnerability path |
| `collectVulnerabilities` | Matches a single software version against all security updates in the bulletin, returning applicable CVEs |
| `CheckVersion` | Thin wrapper around `collectVulnerabilities` for external use |
| `parseOfficeVersion` | Splits a version string like `16.0.19725.20204` into build prefix (`19725`) and build suffix (`20204`) |
| `compareBuildSuffix` | Numerically compares two build suffix strings via zero-padded string comparison |
| `updateVulnsInDB` | Computes the delta between detected and existing vulnerabilities, then applies inserts/deletes |
| `getStoredVulnerabilities` | Fetches currently stored CVEs for a given software ID from the datastore |

## Usage Example

```go
// Run Office vulnerability analysis, collecting newly inserted vulns
vulns, err := winoffice.Analyze(ctx, ds, "/path/to/vulndata", true)
if err != nil {
    log.Fatal(err)
}
for _, v := range vulns {
    fmt.Printf("CVE: %s, SoftwareID: %d, Fixed in: %s\n",
        v.CVE, v.SoftwareID, *v.ResolvedInVersion)
}

// Or check a specific version directly against a bulletin
bulletin, _ := winoffice.CheckVersion("16.0.19725.20100", bulletin)
```

## Version Matching Logic

The analyzer handles two vulnerability scenarios:

1. **Same build prefix** — host is vulnerable if its build suffix is numerically less than the fix's suffix
2. **Different build prefix** — host is vulnerable only if the fix's prefix is numerically greater than the host's prefix (covers version branches with multiple prefixes over time, e.g., LTSC 2024)

An empty bulletin (no security updates) is rejected outright to prevent false-positive remediation of all existing vulnerabilities.
