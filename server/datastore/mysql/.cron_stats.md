MySQL datastore implementation for managing cron job execution statistics, providing CRUD operations and lifecycle management for scheduled and triggered cron runs.

## Key Components

| Function | Description |
|---|---|
| `GetLatestCronStats` | Retrieves up to two records: the most recent scheduled run and the latest pending/queued triggered run |
| `InsertCronStats` | Creates a new cron stats record, returning the inserted row ID |
| `UpdateCronStats` | Updates status and serializes any errors as JSON for a specific stats record |
| `ClaimCronStats` | Atomically assigns a cron stats record to a specific instance by updating status and instance fields |
| `UpdateAllCronStatsForInstance` | Bulk-transitions all records for a given instance from one status to another |
| `CleanupCronStats` | Purges records older than 2 days and marks stale pending/queued jobs as expired |

## Usage Example

```go
// Insert a new scheduled cron stat
id, err := ds.InsertCronStats(ctx,
    fleet.CronStatsTypeScheduled,
    "vulnerabilities",
    "instance-abc123",
    fleet.CronStatsStatusPending,
)

// Claim the record for this instance
err = ds.ClaimCronStats(ctx, id, "instance-abc123", fleet.CronStatsStatusPending)

// Fetch latest stats for a named cron job
stats, err := ds.GetLatestCronStats(ctx, "vulnerabilities")
// stats[0] = most recent scheduled run
// stats[1] = pending/queued triggered run (if any)

// Complete the run, recording any errors
cronErrors := fleet.CronScheduleErrors{}
err = ds.UpdateCronStats(ctx, id, fleet.CronStatsStatusCompleted, &cronErrors)

// Periodic cleanup (called by maintenance scheduler)
err = ds.CleanupCronStats(ctx)
```

## Cleanup Expiration Logic

`CleanupCronStats` runs two operations in a transaction:

- **Hard delete** — removes records older than 2 days
- **Expire stale jobs** — marks pending/queued records as `expired` if they have been running for >2 hours with no active lock, or >12 hours regardless of lock state

> **Note:** Schedules using `WithAltLockID` (e.g., `"leader"`, `"worker"`) store locks under a different name, so they fall back to the 2-hour timeout rather than the lock-based check.
