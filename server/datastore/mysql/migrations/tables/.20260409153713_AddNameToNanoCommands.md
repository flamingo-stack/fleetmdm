Database migration that adds a `name` column to the `nano_commands` table and updates the `nano_view_queue` view to include it.

## Key Components

- **`Up_20260409153713`** — Applies the migration: conditionally adds a nullable `varchar(255)` `name` column to `nano_commands` (using `utf8mb4_unicode_ci` collation), then recreates the `nano_view_queue` view to expose the new column.
- **`Down_20260409153713`** — No-op rollback; the migration is not reversed.
- **`columnExists` check** — Guards the `ALTER TABLE` statement to make the migration idempotent.

## Usage Example

This migration is registered automatically via `init()` and executed by the migration client:

```go
// Registered automatically on package import
MigrationClient.AddMigration(Up_20260409153713, Down_20260409153713)
```

The updated `nano_view_queue` view joins `nano_commands`, `nano_enrollment_queue`, and `nano_command_results`, now surfacing the `name` field alongside existing columns like `command_uuid`, `request_type`, and `status`.

## Notes

- The `name` column defaults to `NULL`, so existing rows are unaffected.
- The view is recreated with `CREATE OR REPLACE`, making it safe to run against a database where the view already exists.
- The `Down` function is intentionally empty — dropping the column would require careful coordination with dependent views and is omitted here.
