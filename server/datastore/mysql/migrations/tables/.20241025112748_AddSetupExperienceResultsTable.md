Database migration that creates the `setup_experience_scripts` and `setup_experience_status_results` tables, and extends `host_script_results` to support Fleet's setup experience feature — tracking script execution, software installs, and VPP app deployments during device enrollment.

## Key Components

### `Up_20241025112748`
Applies three idempotent schema changes:

1. **`setup_experience_scripts` table** — Stores scripts assigned to a team (or globally) that run during device setup. Links to `teams` and `script_contents` via cascading foreign keys, enforcing one script per `global_or_team_id`.

2. **`host_script_results` column + FK** — Adds `setup_experience_script_id` to the existing `host_script_results` table and creates a `SET NULL` foreign key to `setup_experience_scripts`, preserving result rows when the script is deleted.

3. **`setup_experience_status_results` table** — Tracks per-host setup experience state across three integration types:
   - Software installers (`software_installer_id` / `host_software_installs_execution_id`)
   - VPP app installs (`vpp_app_team_id` / `nano_command_uuid`)
   - Setup scripts (`setup_experience_script_id` / `script_execution_id`)

   Each row holds a `status` ENUM (`pending`, `running`, `success`, `failure`) and an optional `error` field.

### `Down_20241025112748`
No-op rollback (returns `nil`).

## Notes

- Column and FK existence checks (`columnExists`, `fkExists`) make the `host_script_results` alterations safe to re-run.
- The `setup_experience_status_results` table is designed for a state machine pattern — each of the three setup endpoints (software install, VPP MDM, scripts) writes its result here upon completion.
