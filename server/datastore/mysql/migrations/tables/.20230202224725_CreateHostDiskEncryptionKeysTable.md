Database migration that creates the `host_disk_encryption_keys` table, storing encrypted disk encryption keys per host with decryptability tracking.

## Key Components

- **`Up_20230202224725`** — Creates the `host_disk_encryption_keys` table with the following schema:

| Column | Type | Description |
|---|---|---|
| `host_id` | `INT UNSIGNED` | Primary key; references the host |
| `base64_encrypted` | `TEXT` | Base64-encoded encrypted disk key |
| `decryptable` | `TINYINT(1) NULL` | `1` = decryptable, `0` = not, `NULL` = unknown |
| `created_at` | `TIMESTAMP` | Record creation time |
| `updated_at` | `TIMESTAMP` | Auto-updated on row change |

- **`Down_20230202224725`** — No-op rollback (table is not dropped).
- **Index** — `idx_host_disk_encryption_keys_decryptable` on `decryptable` to leverage [MySQL's `IS NULL` optimization](https://dev.mysql.com/doc/refman/5.7/en/is-null-optimization.html) for efficiently querying keys with unknown decryptability status.

## Usage Example

This migration is auto-registered via `init()` and applied by the migration client:

```go
// Registered automatically at package load time
MigrationClient.AddMigration(Up_20230202224725, Down_20230202224725)

// Applied during fleet database migration run
// fleet db migrate
```

## Notes

- Migration is **idempotent** (`CREATE TABLE IF NOT EXISTS`).
- The nullable `decryptable` column represents a three-state flag:
  - `NULL` — key fetched, decryptability not yet determined
  - `1` — key can be decrypted by Fleet
  - `0` — key cannot be decrypted
- Rollback is intentionally a no-op; dropping the table would cause data loss.
