Database migration that creates the `mdm_android_commands` table for tracking AMAPI commands issued to Android devices via Fleet's `EnterprisesDevicesService.IssueCommand`.

## Key Components

- **`Up_20260528201143`** — Creates the `mdm_android_commands` table (idempotent via `CREATE TABLE IF NOT EXISTS`) with the following schema:

| Column | Type | Purpose |
|---|---|---|
| `command_uuid` | `VARCHAR(36)` | Primary key; Fleet-generated command identifier |
| `host_uuid` | `VARCHAR(255)` | References the Android host |
| `operation_name` | `VARCHAR(255)` | Full AMAPI operation name used to correlate Pub/Sub `COMMAND` notifications |
| `command_type` | `VARCHAR(32)` | AMAPI command type (e.g. Lock, Wipe, Clear passcode) |
| `status` | `ENUM` | Lifecycle state: `pending`, `acknowledged`, `error` |
| `error_code` | `VARCHAR(64)` | `google.rpc.Code` from Pub/Sub `Operation.Error` |
| `error_message` | `VARCHAR(1024)` | `google.rpc.Status.Message` from AMAPI |
| `created_at` / `updated_at` | `DATETIME(6)` | Microsecond precision; `DATETIME` used over `TIMESTAMP` to avoid Y2K38 issues |

- **`Down_20260528201143`** — No-op rollback (table is left in place).

## Key Design Decisions

- `operation_name` has a **unique index** — it is the correlation key used by `GetMDMAndroidCommandByOperationName` to match incoming Pub/Sub notifications back to the originating Fleet command. Duplicates would cause ambiguous lookups and silent status corruption.
- `host_uuid` has a secondary index (`idx_mdm_android_commands_host_uuid`) for efficient per-device queries.
- `host_mdm_actions.{lock_ref, wipe_ref}` stores the `command_uuid` for Android hosts, mirroring the pattern used for Apple (`nano_commands`) and Windows (`mdm_windows_commands`).
