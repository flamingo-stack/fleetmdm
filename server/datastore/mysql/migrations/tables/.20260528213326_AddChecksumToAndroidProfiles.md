Database migration that adds a `checksum` column to Android MDM profile tables, enabling change detection via MD5 hashing of profile JSON content.

## Key Components

- **`Up_20260528213326`** — Applies the migration with three idempotent steps:
  1. Adds a `BINARY(16)` generated stored column to `mdm_android_configuration_profiles`, computed as `UNHEX(MD5(raw_json))`
  2. Adds a `BINARY(16)` column with default `0` to `host_mdm_android_profiles`
  3. Backfills `host_mdm_android_profiles.checksum` by joining against `mdm_android_configuration_profiles`

- **`Down_20260528213326`** — No-op rollback; columns are not removed on downgrade.

- **`columnExists`** — Guard function (defined elsewhere) used to make the `ALTER TABLE` statements safe to re-run.

## Usage Example

This migration runs automatically via the `MigrationClient` registered in `init()`. To apply manually during development:

```bash
# Apply pending migrations
fleet prepare db --config /etc/fleet/fleet.yml

# Or via direct migration runner
go run ./cmd/fleet/main.go prepare db
```

After migration, the checksum is auto-maintained by MySQL on `mdm_android_configuration_profiles`:

```sql
-- Verify generated checksum column
SELECT profile_uuid, HEX(checksum)
FROM mdm_android_configuration_profiles
LIMIT 5;

-- Verify backfilled host profile checksums
SELECT profile_uuid, HEX(checksum)
FROM host_mdm_android_profiles
LIMIT 5;
```

## Notes

- The generated column on `mdm_android_configuration_profiles` is **STORED**, meaning MySQL computes it on write and indexes are supported.
- The `host_mdm_android_profiles.checksum` is **not** a generated column — it is updated programmatically and seeded by this migration.
