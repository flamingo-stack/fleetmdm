Database migration that creates two tables for tracking operating system information across managed hosts: `operating_systems` (a deduplicated OS catalog) and `host_operating_system` (a mapping of hosts to their OS).

## Key Components

- **`Up_20220713091130`** — Creates two tables:
  - `operating_systems`: Stores unique OS entries identified by `name`, `version`, `arch`, `kernel_version`, and `platform`, with a composite unique key enforcing deduplication. VARCHAR lengths are constrained to satisfy MySQL's max index key length.
  - `host_operating_system`: Maps each host (by `host_id`) to a single OS record (by `os_id`), with a cascading foreign key back to `operating_systems`.
- **`Down_20220713091130`** — No-op rollback (tables are left in place on downgrade).
- **`init`** — Registers the migration with `MigrationClient` at package load time.

## Usage Example

This migration runs automatically via the `MigrationClient` during Fleet's database schema upgrade process. No direct invocation is needed.

```go
// Registration happens automatically on import via init()
MigrationClient.AddMigration(Up_20220713091130, Down_20220713091130)

// Schema created by Up_20220713091130:
//
// operating_systems
//   id            INT UNSIGNED AUTO_INCREMENT PK
//   name          VARCHAR(255)
//   version       VARCHAR(150)
//   arch          VARCHAR(150)
//   kernel_version VARCHAR(150)
//   platform      VARCHAR(50)
//   UNIQUE (name, version, arch, kernel_version, platform)
//
// host_operating_system
//   host_id  INT UNSIGNED PK
//   os_id    INT UNSIGNED → FK operating_systems(id) ON DELETE CASCADE
```

> **Note:** Both `CREATE TABLE` statements use `IF NOT EXISTS`, making this migration safe to re-run (idempotent).
