Adds the `has_acme_payload` column to the `host_mdm_apple_profiles` table, enabling ACME profile detection during certificate list cleanup without requiring access to already-deleted configuration profiles.

## Key Components

- **`Up_20260610172952`** — Idempotent migration that:
  - Conditionally adds a `has_acme_payload TINYINT(1) NOT NULL DEFAULT 0` column to `host_mdm_apple_profiles`
  - Backfills the column by joining against `mdm_apple_configuration_profiles` and flagging rows whose `mobileconfig` payload contains `com.apple.security.acme`
  - Preserves `updated_at` timestamps during the backfill to avoid spurious `ON UPDATE` triggers
- **`Down_20260610172952`** — No-op rollback; the column is left in place on downgrade

## Usage Example

This migration runs automatically via the `MigrationClient` during Fleet's schema upgrade sequence. No manual invocation is required.

```go
// Migration registered on package init
MigrationClient.AddMigration(Up_20260610172952, Down_20260610172952)
```

After applying, rows in `host_mdm_apple_profiles` whose associated `mobileconfig` references the ACME extension will have `has_acme_payload = 1`, allowing the `RemoveProfile` / `CertificateList` trigger logic to identify ACME profiles even after the source configuration profile record has been deleted.

## Notes

- Column addition is guarded by `columnExists` — safe to re-run on already-migrated databases
- The `UPDATE ... JOIN` backfill is inherently idempotent and always executes
