Database migration that creates the `mobile_device_management_solutions` table and adds MDM-related columns and indexes to the `host_mdm` table.

## Key Components

- **`Up_20220802135510`** — Applies the migration:
  - Creates `mobile_device_management_solutions` table (idempotent via `IF NOT EXISTS`) with a unique constraint on `(name, server_url)` to identify distinct Vendor + Server URL combinations
  - Adds a nullable `mdm_id` foreign key column to `host_mdm` (lazy-populated to avoid costly full-table writes on large deployments)
  - Creates `host_mdm_mdm_id_idx` index on `host_mdm.mdm_id`
  - Creates `host_mdm_enrolled_installed_from_dep_idx` composite index on `(enrolled, installed_from_dep)` to accelerate enrollment status queries

- **`Down_20220802135510`** — No-op rollback

## Usage Example

This migration runs automatically via the `MigrationClient` at application startup. To apply manually:

```bash
fleet prepare db --config /etc/fleet/fleet.yml
```

To inspect the resulting schema:

```sql
DESCRIBE mobile_device_management_solutions;
-- id, name, server_url, created_at, updated_at

SHOW INDEX FROM host_mdm;
-- host_mdm_mdm_id_idx
-- host_mdm_enrolled_installed_from_dep_idx
```

## Design Notes

| Decision | Rationale |
|---|---|
| `mdm_id` is `NULL`able | Avoids a blocking full-table update on deployments with many hosts; populated lazily as MDM query results arrive |
| Composite boolean index | Enrollment filter queries combine both `enrolled` and `installed_from_dep`; skewed true/false distribution makes indexing effective |
| Unique key on `(name, server_url)` | The same MDM vendor at different URLs (e.g. two Jamf tenants) produces separate MDM solution records |
