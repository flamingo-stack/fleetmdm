Database migration that drops the foreign key constraint `kernel_host_counts_ibfk_1` from the `kernel_host_counts` table to prevent failures during the vulnerability cron swap-table rebuild process.

## Key Components

| Symbol | Description |
|--------|-------------|
| `Up_20260316120000` | Idempotent migration that drops `kernel_host_counts_ibfk_1` FK if it exists |
| `Down_20260316120000` | No-op rollback; the FK is not restored |
| `init()` | Registers the migration pair with `MigrationClient` |

## Rationale

The FK referencing `software_titles` is unsafe in this context because:

- `kernel_host_counts` is **fully rebuilt** each vulnerability cron run via a swap table
- `CREATE TABLE ... LIKE` does **not** copy foreign keys, so the FK would need manual restoration after every swap
- A `software_title` deleted between the `SELECT` and `ALTER TABLE` would cause the restore to fail
- Orphaned rows are safe — `ListKernelsByOS` queries `JOIN` back to `software_titles`, naturally excluding stale references

## Usage Example

This migration is applied automatically by the Fleet migration runner. To apply or verify manually:

```go
// Migration is registered on package init via MigrationClient
// Run all pending up-migrations:
if err := MigrationClient.Up(db, ""); err != nil {
    log.Fatal(err)
}
```

To check idempotency, the migration calls `constraintExists` before attempting the `ALTER TABLE`, so re-running on a database where the FK was already dropped is safe.
