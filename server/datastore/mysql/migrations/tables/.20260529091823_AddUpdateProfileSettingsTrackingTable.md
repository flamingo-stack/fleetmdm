Database migration that creates the `mdm_configuration_profile_update_settings` table for tracking MDM configuration profiles used for OS update enforcement, with backfill logic for existing Apple declarations and Windows profiles.

## Key Components

- **`Up_20260529091823`** — Creates the tracking table with:
  - Mutually exclusive foreign keys to either `mdm_apple_declarations` or `mdm_windows_configuration_profiles` (enforced via a `CHECK` constraint)
  - Cascading deletes on both FK relationships
  - Backfills existing Apple declarations containing `com.apple.configuration.softwareupdate.enforcement.specific`
  - Backfills existing Windows profiles containing `syncml.FleetOSUpdateTargetLocURI`
  - Skips Fleet-managed system declarations (`Fleet macOS/iOS/iPadOS OS Updates`, `Windows OS Updates`)
- **`Down_20260529091823`** — No-op rollback (table is left in place)

## Table Schema

```text
mdm_configuration_profile_update_settings
├── id                   INT UNSIGNED AUTO_INCREMENT PK
├── windows_profile_uuid VARCHAR(37) NULL → mdm_windows_configuration_profiles
├── apple_declaration_uuid VARCHAR(37) NULL → mdm_apple_declarations
└── created_at           DATETIME(6) DEFAULT CURRENT_TIMESTAMP

Constraints:
  - UNIQUE on each UUID column
  - CHECK: exactly one of the two UUID columns must be non-NULL
  - CASCADE DELETE on both FKs
```

## Usage Example

This migration runs automatically via the `MigrationClient` on `fleet prepare db`:

```go
// Registered in init(); invoked by the migration runner
MigrationClient.AddMigration(Up_20260529091823, Down_20260529091823)
```

To manually apply during development:

```bash
fleet prepare db --config /path/to/config.yml
```

## Notes

- Migration is **idempotent** (`CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`)
- Backfill inspects raw JSON/SyncML payloads to identify update-enforcement profiles without relying on profile names, since names are reserved for Fleet-managed profiles
