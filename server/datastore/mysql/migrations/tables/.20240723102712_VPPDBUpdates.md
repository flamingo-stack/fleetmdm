Database migration creating three VPP (Volume Purchase Program) tables: `vpp_apps`, `vpp_apps_teams`, and `host_vpp_software_installs`.

## Key Components

| Function | Description |
|---|---|
| `Up_20240723102712` | Creates three VPP-related tables (idempotent via `IF NOT EXISTS`) |
| `Down_20240723102712` | No-op rollback (tables are not dropped) |

### Tables Created

**`vpp_apps`** — VPP equivalent of `software_installers`. Caches Apple "Get Assets" metadata and FleetDM app metadata. Keyed on `adam_id` with an optional FK to `software_titles`.

**`vpp_apps_teams`** — Associates VPP apps with specific teams (or global scope when `team_id` is `NULL`). Uses `global_or_team_id` to enforce a unique constraint across nullable team IDs.

**`host_vpp_software_installs`** — VPP equivalent of `host_software_installs`. Tracks per-host MDM install commands, self-service status, and Apple `eventId` from the [Associate Assets](https://developer.apple.com/documentation/devicemanagement/associate_assets) endpoint.

## Notes

- All tables use `utf8mb4_unicode_ci` collation.
- `Down_20240723102712` is intentionally a no-op — dropping these tables is considered unsafe for automated rollback.
- `vpp_apps_teams.global_or_team_id` defaults to `0` (global) to work around MySQL's inability to enforce uniqueness across `NULL` values in a composite index.
