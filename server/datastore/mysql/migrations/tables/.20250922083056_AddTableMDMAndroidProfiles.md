Database migration that creates and modifies tables to support Android MDM (Mobile Device Management) configuration profiles in Fleet.

## Key Components

- **`Up_20250922083056`** — Applies the migration, performing the following operations:
  - Creates `mdm_android_configuration_profiles` — stores Android MDM profiles as JSON with team scoping and upsert-friendly `AUTO_INCREMENT` tracking
  - Creates `android_policy_requests` — audits AMAPI (Android Management API) requests with status codes, error details, and policy versioning
  - Creates `host_mdm_android_profiles` — links hosts to profiles with delivery status, operation type, failure counts, and dual request UUID references
  - Alters `mdm_configuration_profile_labels` — adds `android_profile_uuid` column, a new unique index, a foreign key, and a three-platform `CHECK` constraint (Apple / Windows / Android), then drops the legacy two-platform constraint if present
  - Alters `android_devices` — adds `applied_policy_id` and `applied_policy_version`, migrates data from the old `android_policy_id` column, then drops it
  - Backfills `hosts.uuid` for pre-existing Android hosts using `enterprise_specific_id`

- **`Down_20250922083056`** — No-op rollback (migration is intended to be permanent)

## Usage Example

This file is automatically registered via `init()` and executed by the migration client:

```go
// Registration (automatic via init())
MigrationClient.AddMigration(Up_20250922083056, Down_20250922083056)

// Triggered by the Fleet migration runner (not called directly)
// fleet prepare db --config fleet.yml
```

> **Note:** The migration is idempotent — all `CREATE TABLE` statements use `IF NOT EXISTS` and column additions are guarded by `columnExists` / `columnsExists` checks, making it safe to re-run.
