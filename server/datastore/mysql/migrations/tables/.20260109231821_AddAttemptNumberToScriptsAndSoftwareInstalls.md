Database migration that adds an `attempt_number` column and a `(host_id, policy_id)` composite index to both `host_script_results` and `host_software_installs` tables, enabling retry tracking for scripts and software installs.

## Key Components

| Symbol | Description |
|---|---|
| `Up_20260109231821` | Applies the migration: adds `attempt_number INT DEFAULT NULL` and composite indexes to both tables |
| `Down_20260109231821` | No-op rollback (schema changes are not reversed) |
| `init()` | Registers the migration with `MigrationClient` |

## Schema Changes

**Columns added (idempotent):**

```text
host_script_results.attempt_number       INT DEFAULT NULL
host_software_installs.attempt_number    INT DEFAULT NULL
```

**Indexes added (idempotent):**

```text
idx_host_script_results_host_policy      (host_id, policy_id)
idx_host_software_installs_host_policy   (host_id, policy_id)
```

## Usage Example

This migration runs automatically via the `MigrationClient`. To apply manually:

```bash
fleet prepare db --config /etc/fleet/fleet.yml
```

## Notes

- All changes are **idempotent** — `columnExists` and `indexExistsTx` guards prevent duplicate-column or duplicate-index errors on re-runs.
- The `attempt_number` field supports retry logic by tracking how many times a script or software install has been attempted on a host.
- The composite `(host_id, policy_id)` indexes optimize queries that filter or join on both host and policy, common in policy-driven remediation workflows.
- The rollback (`Down_`) is intentionally empty; dropping columns in production is considered unsafe without explicit intervention.
