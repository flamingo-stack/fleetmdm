Database migration that creates two tables for tracking MDM enrollment status and Munki version information per host.

## Key Components

- **`Up_20211216131203`** — Creates the `host_mdm` and `host_munki_info` tables using `CREATE TABLE IF NOT EXISTS` (idempotent).
- **`Down_20211216131203`** — No-op rollback; tables are not dropped on downgrade.
- **`init`** — Registers the migration with `MigrationClient`.

### Tables Created

| Table | Columns | Description |
|---|---|---|
| `host_mdm` | `host_id`, `enrolled`, `server_url`, `installed_from_dep` | MDM enrollment state per host |
| `host_munki_info` | `host_id`, `version` | Munki agent version per host |

Both tables use `host_id` as the primary key with `InnoDB` / `utf8mb4_unicode_ci`.

## Usage Example

This migration is applied automatically by the migration client at startup. To run manually:

```bash
# Apply migration
fleet prepare db --config /path/to/config.yml

# Verify tables exist
mysql -u fleet -p fleet -e "SHOW TABLES LIKE 'host_mdm';"
mysql -u fleet -p fleet -e "DESCRIBE host_munki_info;"
```

To reference the schema in Go:

```go
// Query MDM enrollment for a host
row := db.QueryRow(
    `SELECT enrolled, server_url, installed_from_dep FROM host_mdm WHERE host_id = ?`,
    hostID,
)

// Query Munki version for a host
row := db.QueryRow(
    `SELECT version FROM host_munki_info WHERE host_id = ?`,
    hostID,
)
```

> **Note:** The down migration is intentionally a no-op. To reverse this migration manually, drop `host_mdm` and `host_munki_info` from your database.
