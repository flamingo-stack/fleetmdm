Database migration that removes duplicate rows from the `software_cve` table and adds a unique constraint on `(software_id, cve)` to prevent future duplicates.

## Key Components

| Function | Description |
|---|---|
| `Up_20220708095046` | Migration entry point — acquires a vulnerability lock, removes duplicates, and adds the unique constraint |
| `Down_20220708095046` | No-op rollback (constraint removal is not automated) |
| `removeDups` | Deletes duplicate `software_cve` rows, keeping the highest `id` per `(cve, software_id)` pair |
| `addUniqConstraint` | Idempotently adds `UNIQUE (software_id, cve)` constraint via `ALGORITHM=INPLACE, LOCK=NONE` |
| `acquireLock` | Acquires a named advisory lock in the `locks` table (30-minute TTL) to guard the dedup window |
| `releaseLock` | Removes the advisory lock record by `name` and `owner` |

## Migration Strategy

The migration is designed to be idempotent and safe for live databases:

1. **Lock acquisition** — A random 64-character identifier is generated and used to claim the `vulnerabilities` lock, preventing the vulnerability scanner from inserting new duplicates between the dedup and constraint steps. If the lock cannot be acquired, migration proceeds with a warning.
2. **Duplicate removal** — A `DELETE ... JOIN` statement removes all but the highest-`id` row for each `(cve, software_id)` group.
3. **Constraint creation** — Uses `ALGORITHM=INPLACE, LOCK=NONE` for an online DDL operation with minimal table locking.
