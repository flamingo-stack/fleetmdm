Database migration that fixes Windows MDM profiles stuck in unverified states by transitioning them to a verified status.

## Key Components

- **`Up_20260316120004`** — Applies two idempotent SQL updates to correct profile delivery statuses in `host_mdm_windows_profiles`:
  1. Moves all records with status `MDMDeliveryVerifying` → `MDMDeliveryVerified`
  2. Moves records with status `MDMDeliveryFailed` and a specific `detail` of `HostMDMProfileDetailFailedWasVerifying` → `MDMDeliveryVerified`, clearing the `detail` field
- **`Down_20260316120004`** — No-op rollback (migration is considered safe to leave in place)

## Usage Example

This migration runs automatically via `MigrationClient` on server startup. No manual invocation is needed.

```go
// Executed internally by the migration runner:
Up_20260316120004(tx)
```

To apply manually during development:

```bash
fleet prepare db --config /path/to/config.yml
```

## Notes

- **Idempotent:** Safe to re-run; uses `UPDATE ... WHERE status = ?` which is a no-op if no matching rows exist.
- **Scope:** Targets only `host_mdm_windows_profiles`; macOS profiles are unaffected.
- The second step specifically handles profiles that previously failed *because* they were stuck in a verifying state (`HostMDMProfileDetailFailedWasVerifying`), cleaning up the stale `detail` message alongside the status correction.
