Database migration that creates the `vpp_tokens` table and migrates existing VPP token data to support multiple VPP tokens per Fleet instance.

## Key Components

- **`Up_20240829165605`** — Forward migration that:
  1. Creates the `vpp_tokens` table with team assignment logic (`team_id` + `null_team_type` enum)
  2. Adds `vpp_token_id` FK column to `host_vpp_software_installs`
  3. Migrates any existing VPP token from `mdm_config_assets` into the new table (defaulting to `allteams`)
  4. Soft-deletes the deprecated token from `mdm_config_assets`
  5. Backfills `vpp_token_id` on all existing host install records
  6. Enqueues a `db_migration/migrate_vpp_token` worker job to backfill token metadata (organization name, location, renew date) that requires the decryption key unavailable at migration time

- **`Down_20240829165605`** — No-op rollback

## Key Design Decisions

| Decision | Rationale |
|---|---|
| Team uniqueness enforced in Go, not DB | Handling `NULL` team IDs with `none`/`allteams`/`noteam` enum states made SQL constraints unwieldy |
| `ON DELETE SET NULL` + `null_team_type = 'none'` | Ensures token becomes inactive automatically when its team is deleted |
| `INSERT IGNORE` | Makes the migration idempotent |
| Hardcoded job timestamps | Keeps `schema.sql` stable across runs |

## Usage Example

This migration runs automatically via the Fleet migration client:

```go
// Registered automatically via init()
MigrationClient.AddMigration(Up_20240829165605, Down_20240829165605)
```

To apply manually during development:

```bash
fleet prepare db --config /path/to/config.yml
```

> **Note:** Token metadata (`organization_name`, `location`, `renew_at`) is backfilled asynchronously by the `migrate_vpp_token` worker job, since decrypting the stored token requires `Server.PrivateKey` which is unavailable during SQL migration execution.
