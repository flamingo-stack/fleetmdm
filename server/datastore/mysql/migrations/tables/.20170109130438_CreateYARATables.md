Database migration that creates three YARA-related tables for file integrity monitoring and signature management.

## Key Components

- **`Up_20170109130438`** — Creates three InnoDB tables (idempotent via `IF NOT EXISTS`):
  - `yara_signatures` — Stores unique YARA signature names with auto-increment IDs
  - `yara_file_paths` — Join table linking file integrity monitoring records to YARA signatures via composite primary key and foreign keys
  - `yara_signature_paths` — Maps file paths to YARA signatures with cascading deletes
- **`Down_20170109130438`** — Drops all three tables in dependency-safe order (`yara_signature_paths` → `yara_file_paths` → `yara_signatures`)
- **`init()`** — Registers both migration functions with `MigrationClient`

## Schema Relationships

```text
file_integrity_monitorings
        │
        └─► yara_file_paths ◄─── yara_signatures
                                        │
                                        └─► yara_signature_paths
                                            (CASCADE DELETE)
```

## Usage Example

```go
// Migration is auto-registered via init(); no direct invocation needed.
// The MigrationClient applies it during database setup:

err := MigrationClient.Up(db)
if err != nil {
    log.Fatal("migration failed:", err)
}

// To roll back:
err = MigrationClient.Down(db)
```

## Notes

- All tables use `ENGINE=InnoDB` with `utf8` charset
- `yara_signature_paths` enforces `ON DELETE CASCADE` from `yara_signatures`, ensuring orphaned file paths are automatically cleaned up
- Rollback drops tables in reverse dependency order to avoid foreign key constraint violations
