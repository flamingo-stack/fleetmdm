Database migration that creates the `email_changes` table for tracking pending user email address change requests.

## Key Components

- **`Up_20170124230432`** — Creates the `email_changes` table with the following schema:
  - `id` — Auto-incrementing primary key
  - `user_id` — Foreign key referencing `users.id` with cascade delete
  - `token` — Unique 128-character token used to verify the email change
  - `new_email` — The requested new email address
  - Uses `InnoDB` engine with `utf8mb4_unicode_ci` collation; operation is idempotent (`CREATE TABLE IF NOT EXISTS`)

- **`Down_20170124230432`** — Drops the `email_changes` table if it exists

- **`init`** — Registers both migration functions with `MigrationClient`

## Usage Example

```go
// Migrations are registered automatically via init() and run by the migration client.
// To apply this migration:
MigrationClient.AddMigration(Up_20170124230432, Down_20170124230432)

// The resulting table supports queries such as:
// SELECT * FROM email_changes WHERE token = ? AND user_id = ?
// DELETE FROM email_changes WHERE user_id = ?  -- also cascades on user deletion
```

## Notes

- The unique index on `token` (`idx_unique_email_changes_token`) prevents duplicate pending requests using the same token.
- Cascade delete on `user_id` ensures orphaned email change records are automatically cleaned up when a user is removed.
