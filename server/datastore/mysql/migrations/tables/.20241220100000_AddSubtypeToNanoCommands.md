Database migration that adds a `subtype` enum column to the `nano_commands` table and removes an XML validation constraint to support MDM profiles containing secret variables.

## Key Components

- **`Up_20241220100000(tx *sql.Tx) error`** — Applies the migration with two idempotent operations:
  - Adds a `subtype` enum column (`none` | `profile_with_secrets`) to `nano_commands`, defaulting to `none`
  - Drops the `nano_commands_chk_3` constraint that enforced XML validation on command data (incompatible with whole-profile secret variables like `$FLEET_SECRET_PROFILE`)
- **`Down_20241220100000(_ *sql.Tx) error`** — No-op rollback; the migration is not reversed

## Usage Example

```go
// Migration is registered automatically via init()
// and executed by the MigrationClient during fleet server startup.

// After migration, nano_commands rows carry a subtype field:
// INSERT INTO nano_commands (command_uuid, request_type, command, subtype)
// VALUES (?, ?, ?, 'profile_with_secrets')

// Enum values sourced from the nanomdm/mdm package:
// mdm.CommandSubtypeNone             → "none"
// mdm.CommandSubtypeProfileWithSecrets → "profile_with_secrets"
```

## Notes

- Both operations are **idempotent**: `columnExists` and `constraintExists` guards prevent errors on re-runs
- The dropped `nano_commands_chk_3` constraint previously rejected non-XML command payloads; removing it allows storing profiles that consist entirely of a single secret placeholder (e.g., `$FLEET_SECRET_PROFILE`)
- No down migration is implemented — reversing requires a manual schema change
