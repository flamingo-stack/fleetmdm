Database migration that adds `ON DELETE CASCADE` foreign key constraints to the `host_software` table, ensuring orphaned records are automatically cleaned up when referenced `hosts` or `software` rows are deleted.

## Key Components

- **`Up_20210819131107`** — Forward migration that idempotently rewrites the `host_software` table with cascading foreign keys on both `host_id → hosts(id)` and `software_id → software(id)`.
- **`Down_20210819131107`** — No-op rollback; cascade constraints are not removed on downgrade.
- **`init`** — Registers both migration functions with `MigrationClient`.

## Migration Strategy

The migration uses a create-copy-rename pattern instead of `ALTER TABLE` in-place or `CREATE TEMPORARY TABLE` (the latter caused issues with MySQL GTID replication — see upstream [issue #2462](https://github.com/fleetdm/fleet/issues/2462)):

```text
1. Drop existing FKs on host_software (idempotent check)
2. CREATE TABLE IF NOT EXISTS temp_host_software LIKE host_software
3. Add cascading FKs to temp_host_software
4. INSERT IGNORE INTO temp_host_software SELECT * FROM host_software
   (purges orphaned rows that violate the new constraints)
5. DROP TABLE IF EXISTS host_software
6. RENAME TABLE temp_host_software TO host_software
```

## Usage Example

This migration runs automatically via the `MigrationClient` on `fleet db migrate`:

```go
// Registered automatically in init()
MigrationClient.AddMigration(Up_20210819131107, Down_20210819131107)
```

> **Note:** The migration is idempotent — it checks for existing foreign keys via `fkExists` and `constraintsForTable` before dropping or re-adding them, making it safe to re-run.
