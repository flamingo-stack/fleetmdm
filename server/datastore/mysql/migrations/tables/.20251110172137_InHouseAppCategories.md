Database migration that creates the `in_house_app_software_categories` junction table, establishing a many-to-many relationship between in-house apps and software categories.

## Key Components

- **`Up_20251110172137`** — Creates the `in_house_app_software_categories` table with cascade-delete foreign keys referencing `in_house_apps` and `software_categories`. Migration is idempotent via `CREATE TABLE IF NOT EXISTS`.
- **`Down_20251110172137`** — No-op rollback (table is not dropped on down migration).
- **`init`** — Registers both migration functions with `MigrationClient`.

## Schema Created

```text
in_house_app_software_categories
├── id                    UNSIGNED INT  (PK, AUTO_INCREMENT)
├── software_category_id  UNSIGNED INT  (FK → software_categories.id, CASCADE DELETE)
├── in_house_app_id       UNSIGNED INT  (FK → in_house_apps.id, CASCADE DELETE)
└── created_at            DATETIME(6)   (DEFAULT CURRENT_TIMESTAMP)

UNIQUE: (in_house_app_id, software_category_id)
```

## Usage Example

This migration runs automatically via the migration client at startup. To apply manually:

```bash
fleet prepare db --config /etc/fleet/fleet.yml
```

To reference the migration in code:

```go
// Migration is registered automatically via init()
// MigrationClient will execute Up_20251110172137 during schema upgrades
MigrationClient.AddMigration(Up_20251110172137, Down_20251110172137)
```

## Notes

- Deleting either an `in_house_app` or a `software_category` record will automatically remove associated rows in this table via `ON DELETE CASCADE`.
- The unique constraint prevents duplicate category assignments for the same app.
