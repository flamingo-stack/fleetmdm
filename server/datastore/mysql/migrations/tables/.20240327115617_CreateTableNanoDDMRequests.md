Database migration that creates the `mdm_apple_declarative_requests` table for storing Apple MDM Declarative Device Management (DDM) request records.

## Key Components

- **`Up_20240327115617`** — Creates the `mdm_apple_declarative_requests` table with the following schema:

| Column | Type | Description |
|---|---|---|
| `id` | `INT UNSIGNED AUTO_INCREMENT` | Primary key |
| `created_at` | `TIMESTAMP` | Record creation timestamp |
| `enrollment_id` | `VARCHAR(255)` | Foreign key to `nano_enrollments.id` (CASCADE delete) |
| `message_type` | `VARCHAR(255)` | DDM message type (`tokens`, `declaration-items`, `status`, or `declaration/…/…`) |
| `raw_json` | `TEXT` | Raw JSON payload of the declarative request |

- **`Down_20240327115617`** — No-op rollback (table is not dropped on rollback).
- Migration is **idempotent** via `CREATE TABLE IF NOT EXISTS`.

## Usage Example

This migration is registered automatically via `init()` and executed by the migration client:

```go
// Registered automatically on package import
MigrationClient.AddMigration(Up_20240327115617, Down_20240327115617)

// Applied as part of the standard migration run
err := MigrationClient.Up(db, targetVersion)
```

## Notes

- Uses `utf8mb4_unicode_ci` collation throughout for full Unicode support.
- The `enrollment_id` foreign key enforces referential integrity against `nano_enrollments`, with cascading deletes ensuring request records are cleaned up when an enrollment is removed.
- `Down_20240327115617` is intentionally empty — dropping the table on rollback is not implemented.
