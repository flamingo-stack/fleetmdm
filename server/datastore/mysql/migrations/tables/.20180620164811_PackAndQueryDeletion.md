Database migration that cleans up dangling `scheduled_queries` records and replaces loose foreign key constraints with cascading delete constraints for both `query_name` and `pack_id` references.

## Key Components

- **`Up_20180620164811(tx *sql.Tx) error`** — Applies the migration in four idempotent steps:
  1. Drops the legacy foreign key `scheduled_queries_ibfk_1` if it exists (non-fatal on failure)
  2. Deletes orphaned `scheduled_queries` rows whose `pack_id` no longer exists in `packs`
  3. Adds `scheduled_queries_query_name` FK → `queries(name)` with `ON DELETE CASCADE`
  4. Adds `scheduled_queries_pack_id` FK → `packs(id)` with `ON DELETE CASCADE`

- **`Down_20180620164811(tx *sql.Tx) error`** — No-op rollback; the migration is considered irreversible.

- **`init()`** — Registers both migration functions with `MigrationClient`.

## Usage Example

This migration is automatically applied by the migration runner — no direct invocation is required. It is designed to be idempotent: each structural change is guarded by a `fkExists` check before execution.

```go
// Applied automatically during fleet schema migration:
// fleet prepare db

// Manual inspection of affected constraints:
// SHOW CREATE TABLE scheduled_queries;
```

## Notes

- Uses `fkExists()` (defined elsewhere in the `tables` package) to guard each `ALTER TABLE` statement, making re-runs safe.
- The legacy FK drop (`scheduled_queries_ibfk_1`) is intentionally non-fatal — a logged warning is emitted instead of returning an error, accommodating environments where the constraint name differs.
