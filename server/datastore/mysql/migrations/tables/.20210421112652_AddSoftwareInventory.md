Database migration that creates the software inventory schema, introducing `software` and `host_software` tables to track installed software across managed hosts.

## Key Components

- **`Up_20210421112652`** — Creates two tables:
  - `software`: Stores unique software entries (name, version, source) with a `bigint` primary key for high-volume auto-increment and a composite unique index on `(name, version, source)`
  - `host_software`: Join table linking hosts to their installed software via a composite primary key `(host_id, software_id)`
- **`Down_20210421112652`** — No-op rollback (tables are not dropped)
- **`init()`** — Registers the migration with `MigrationClient`

## Schema Details

```sql
-- Deduplicated software catalog
CREATE TABLE software (
  id         BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  name       VARCHAR(255) NOT NULL,
  version    VARCHAR(255) NOT NULL DEFAULT '',
  source     VARCHAR(64)  NOT NULL,
  UNIQUE KEY idx_name_version (name, version, source)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- Many-to-many: hosts <-> software
CREATE TABLE host_software (
  host_id     INT UNSIGNED    NOT NULL REFERENCES hosts(id),
  software_id BIGINT UNSIGNED NOT NULL REFERENCES software(id),
  PRIMARY KEY (host_id, software_id)
);
```

## Notes

- Migration is **idempotent** (`CREATE TABLE IF NOT EXISTS`), safe to re-run
- `bigint` is used for `software.id` to accommodate high row volumes from deduplication across many hosts
- `source` distinguishes software origins (e.g., `homebrew`, `deb`, `rpm`)
- Rollback is intentionally a no-op — dropping these tables would cause data loss
