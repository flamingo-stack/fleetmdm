Database migration that introduces policy automation iteration tracking for existing policy violations.

## Key Components

- **`Up_20221216115820`** — Creates the `policy_automation_iterations` table and adds the `automation_iteration` column to `policy_membership`. The migration is idempotent via `CREATE TABLE IF NOT EXISTS` and a `columnExists` guard.
- **`Down_20221216115820`** — No-op rollback; schema changes are not reversed.
- **`init`** — Registers the migration with `MigrationClient`.

### Schema Changes

| Object | Change |
|---|---|
| `policy_automation_iterations` | New table: `policy_id` (PK, FK → `policies.id` CASCADE DELETE), `iteration INT NOT NULL` |
| `policy_membership` | New nullable column: `automation_iteration INT NULL` |

This migration runs automatically via the `MigrationClient` during database initialization. No manual invocation is required.

// The Up function is idempotent and safe to re-run:
// - Uses CREATE TABLE IF NOT EXISTS

## Notes

- The `policy_automation_iterations` table tracks which automation iteration a policy is currently on, enabling Fleet to process pre-existing violations when a policy automation is first configured.
- `automation_iteration` on `policy_membership` allows per-host tracking of which iteration triggered the automation, preventing duplicate notifications for the same violation.
