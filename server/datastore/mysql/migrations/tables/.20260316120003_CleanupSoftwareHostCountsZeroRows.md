Database migration that removes accumulated zero-count rows from `software_host_counts` and `software_titles_host_counts` tables, then adds CHECK constraints to prevent future zero-count inserts.

## Key Components

- **`Up_20260316120003`** — Runs the forward migration in idempotent steps:
  1. Deletes rows where `hosts_count = 0` from both tables
  2. Adds `CHECK (hosts_count > 0)` constraints if not already present, using `constraintExists` as the idempotency guard
- **`Down_20260316120003`** — No-op rollback; constraints and deleted rows are not restored
- **Unnamed CHECK constraints** — Intentionally unnamed so `CREATE TABLE ... LIKE` (used by the atomic swap table pattern) copies them without name drift across swaps. MySQL auto-names them `<table>_chk_1`

## Usage Example

This migration is registered automatically via `init()` and executed by the migration client:

```go
// Registered automatically on package import
MigrationClient.AddMigration(Up_20260316120003, Down_20260316120003)

// Run via standard migration tooling
// e.g. fleet db migrate
```

To verify the constraints were applied after migration:

```sql
SELECT CONSTRAINT_NAME, CHECK_CLAUSE
FROM information_schema.CHECK_CONSTRAINTS
WHERE TABLE_NAME IN ('software_host_counts', 'software_titles_host_counts');
```

## Notes

- Safe to re-run; `constraintExists` prevents duplicate `ALTER TABLE` calls
- The accompanying sync process uses an atomic swap table pattern that no longer produces zero-count rows, making the deleted data non-recoverable without a full resync
