Database migration that creates two tables supporting batch script execution tracking: `batch_script_executions` and `batch_script_execution_host_results`.

## Key Components

- **`Up_20250424153059`** — Creates the two batch script tables using `IF NOT EXISTS` for idempotency. The down migration is a no-op.
- **`batch_script_executions`** — Stores batch-level execution records, linking a `script_id` (FK → `scripts.id`) to a unique `execution_id`, with optional `user_id` and timestamps.
- **`batch_script_execution_host_results`** — Stores per-host results for a given batch, linking `batch_execution_id` (FK → `batch_script_executions.execution_id`) to a `host_id`, an optional `host_execution_id`, and an optional `error` field.

## Schema Overview

```text
batch_script_executions
├── id (PK, AUTO_INCREMENT)
├── script_id (FK → scripts.id, CASCADE DELETE)
├── execution_id (UNIQUE)
├── user_id (nullable)
└── created_at / updated_at

batch_script_execution_host_results
├── id (PK, AUTO_INCREMENT)
├── batch_execution_id (FK → batch_script_executions.execution_id, CASCADE DELETE)
├── host_id
├── host_execution_id (nullable)
├── error (nullable)
└── created_at / updated_at
```
