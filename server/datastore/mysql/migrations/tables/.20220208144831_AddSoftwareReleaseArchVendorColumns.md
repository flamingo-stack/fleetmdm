Database migration that adds `release`, `vendor`, and `arch` columns to the `software` table, updates the unique key to include these new fields, and adds a composite index for vulnerability post-processing queries.

## Key Components

- **`Up_20220208144831`** — Applies the migration with the following steps:
  1. Adds `release` (VARCHAR 64), `vendor` (VARCHAR 32), and `arch` (VARCHAR 16) columns if they don't exist
  2. Drops the existing unique key on `software.name`
  3. Adds a new composite unique key on `(name, version, source, release, vendor, arch)`
  4. Purges all `rpm_packages` rows (to force re-ingestion with new osquery fields)
  5. Creates a `software_source_vendor_idx` index on `(source, vendor)` for vulnerability post-processing
- **`Down_20220208144831`** — No-op rollback; columns and indexes are not removed
- **`init`** — Registers the migration with `MigrationClient`

## Usage Example

```go
// Applied automatically via MigrationClient on startup.
// To run manually during development:
db, _ := sql.Open("mysql", dsn)
tx, _ := db.Begin()

if err := Up_20220208144831(tx); err != nil {
    tx.Rollback()
    log.Fatal(err)
}
tx.Commit()
```

## Notes

- Migration is **idempotent** — uses `columnsExists` and `indexExistsTx` guards before executing DDL
- Column lengths are intentionally short (64/32/16) to stay within MySQL's 3072-byte key size limit
- All new columns are `NOT NULL DEFAULT ''` since they participate in the unique key
- RPM package data is cleared on upgrade; re-ingestion relies on updated osquery query fields
