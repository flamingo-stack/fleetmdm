Database migration that creates the `scim_last_request` table, a singleton table designed to store the status and details of the most recent SCIM (System for Cross-domain Identity Management) request.

## Key Components

| Symbol | Description |
|--------|-------------|
| `Up_20250408133233` | Creates the `scim_last_request` table if it does not already exist |
| `Down_20250408133233` | No-op rollback (table is left in place on downgrade) |

### Table Schema: `scim_last_request`

| Column | Type | Notes |
|--------|------|-------|
| `id` | `TINYINT(1) UNSIGNED` | Primary key, hardcoded default `1` — enforces single-row constraint |
| `status` | `VARCHAR(31)` | Short status string for the last SCIM request |
| `details` | `VARCHAR(255)` | Additional detail or error message |
| `created_at` | `DATETIME(6)` | Row creation timestamp (microsecond precision) |
| `updated_at` | `DATETIME(6)` | Auto-updated on every write |

## Usage Example

This migration is registered automatically via `init()` and is executed by the migration client during database setup or upgrade:

```go
// Registered automatically on package import; no direct call needed.
// The migration client runs pending migrations in timestamp order.
MigrationClient.AddMigration(Up_20250408133233, Down_20250408133233)
```

To apply manually during development:

```bash
# Run all pending migrations
fleet prepare db --dev
```

## Notes

- The migration is **idempotent** (`CREATE TABLE IF NOT EXISTS`), so it is safe to run multiple times.
- The singleton pattern (fixed `id = 1`) means callers should use `INSERT ... ON DUPLICATE KEY UPDATE` to update the row rather than inserting new rows.
- The `Down` function is intentionally a no-op; data loss risk is considered acceptable for this audit/status table.
