Database migration that creates the `host_scd_data` table for unified SCD (Slowly Changing Dimension) chart dataset storage and backfills `historical_data` feature flags to `true` across AppConfig and all team configurations.

## Key Components

- **`Up_20260423161823`** — Applies the migration with three operations:
  1. Creates the `host_scd_data` table — an interval-based bitmap store supporting two write strategies: *Accumulate* (OR-merge within a bucket, used for uptime) and *Snapshot* (open rows until state changes, used for CVEs).
  2. Backfills `AppConfig.Features.HistoricalData.Uptime` and `.Vulnerabilities` to `true` via `updateAppConfigJSON`.
  3. Patches every team's `config` JSON using `JSON_MERGE_PATCH` to set `features.historical_data.{uptime,vulnerabilities}` to `true` without touching unrelated keys.

- **`Down_20260423161823`** — No-op rollback (table drop and config revert are not automated).

- **`host_scd_data` schema** — Key fields:

| Column | Type | Purpose |
|---|---|---|
| `dataset` | `VARCHAR(50)` | Chart dataset name |
| `entity_id` | `VARCHAR(100)` | Scoped entity within a dataset |
| `host_bitmap` | `MEDIUMBLOB` | Compressed host membership bitmap |
| `valid_from` / `valid_to` | `DATETIME` | Interval bounds; open rows use sentinel `9999-12-31` |

## Usage Example

This migration runs automatically via the Fleet migration client on `fleet prepare db` or server startup. No manual invocation is needed.

```go
// Registered automatically via init()
MigrationClient.AddMigration(Up_20260423161823, Down_20260423161823)
```

The read/write paths for `host_scd_data` are implemented in `server/chart/internal/mysql/data.go`. The `JSON_MERGE_PATCH` approach ensures team configs are updated safely without re-marshalling the full `TeamConfig` struct, which would zero-out unset fields.
