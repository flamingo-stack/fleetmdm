Database migration that changes the `label_id` foreign key constraint on `mdm_configuration_profile_labels` and `mdm_declaration_labels` tables from `ON DELETE SET NULL` to `ON DELETE RESTRICT`, preventing label deletion when referenced by MDM configuration profiles or declarations.

## Key Components

- **`Up_20260603101320`** — Applies the migration: validates no orphaned `label_id` values exist, drops the existing `labels` foreign key on each table, and re-adds it with `ON DELETE RESTRICT`
- **`Down_20260603101320`** — No-op rollback (intentionally empty)
- **Orphan pre-check** — Guards both tables against data inconsistency before altering constraints, returning a descriptive error if any `label_id` references a non-existent label
- **Idempotency** — Uses `constraintExists` checks before dropping or adding constraints, making the migration safe to re-run

## Usage Example

```go
// Migration is registered automatically via init()
// and executed by the migration client in sequence.

// The Up function enforces referential integrity by replacing:
//   FOREIGN KEY (label_id) REFERENCES labels (id) ON DELETE SET NULL
// with:
//   FOREIGN KEY (label_id) REFERENCES labels (id) ON DELETE RESTRICT

// Attempting to delete a label that is still referenced by a
// configuration profile or declaration will now fail at the DB level.
```

## Notes

- Targets two tables: `mdm_configuration_profile_labels` and `mdm_declaration_labels`
- Named constraints (`mdm_configuration_profile_labels_ibfk_label`, `mdm_declaration_labels_ibfk_label`) are used to ensure idempotent re-runs skip already-applied changes
- The rollback is intentionally a no-op — reverting to `ON DELETE SET NULL` is considered unsafe without explicit data review
