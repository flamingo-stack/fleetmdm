Database migration that backfills `attempt_number = 0` for existing policy automation records in `host_script_results` and `host_software_installs` where the field is `NULL` but execution has already occurred (indicated by a non-null exit code).

## Key Components

- **`Up_20260124200020`** — Runs two idempotent `UPDATE` statements:
  - Sets `attempt_number = 0` on `host_script_results` rows where `attempt_number IS NULL` and `exit_code IS NOT NULL`
  - Sets `attempt_number = 0` on `host_software_installs` rows where `attempt_number IS NULL` and `install_script_exit_code IS NOT NULL`
- **`Down_20260124200020`** — No-op rollback; the migration is safe to leave in place.
- **`init()`** — Registers both functions with `MigrationClient`.

## Usage Example

This migration runs automatically via the Fleet migration runner. No manual invocation is needed.

```bash
# Apply all pending migrations (including this one)
fleet prepare db --config /etc/fleet/fleet.yml
```

## Notes

- **Idempotent** — Uses `WHERE ... IS NULL` guards, so re-running produces no unintended side effects.
- **No schema changes** — Pure data backfill; no `ALTER TABLE` or index modifications.
- **Context** — Targets records created before `attempt_number` tracking was introduced, ensuring consistent state for policy automation retry logic.
