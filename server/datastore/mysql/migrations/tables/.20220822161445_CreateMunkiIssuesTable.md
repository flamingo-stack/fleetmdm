Database migration that creates the `munki_issues` and `host_munki_issues` tables for tracking Munki warning/error messages associated with managed hosts.

## Key Components

- **`Up_20220822161445`** — Creates two tables:
  - `munki_issues`: Stores unique Munki warning/error messages with a composite unique index on `(name, issue_type)`
  - `host_munki_issues`: Junction table linking hosts to their Munki issues via a composite primary key `(host_id, munki_issue_id)`
- **`Down_20220822161445`** — No-op rollback (tables are not dropped)
- **`init`** — Registers the migration with `MigrationClient`

## Schema

```sql
-- Deduplicated Munki warning/error messages
CREATE TABLE munki_issues (
    id         INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,   -- error/warning message text
    issue_type VARCHAR(10) NOT NULL,    -- "warning" or "error"
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY idx_munki_issues_name (name, issue_type)
);

-- Many-to-many: hosts <-> munki_issues
CREATE TABLE host_munki_issues (
    host_id        INT(10) UNSIGNED NOT NULL,
    munki_issue_id INT(10) UNSIGNED NOT NULL,
    created_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (host_id, munki_issue_id)
);
```

## Notes

- Both `CREATE TABLE` statements use `IF NOT EXISTS`, making the migration **idempotent**
- `name` is capped at 255 characters — sufficient for observed Munki messages (~80 chars max); a hash column can be added later if needed
- `issue_type` avoids the reserved keyword `type`
