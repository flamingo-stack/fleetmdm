Database migration that adds an `os_version_id` column to the `operating_systems` table and backfills it with integer IDs derived from distinct name/version combinations.

## Key Components

- **`Up_20240130115133`** — Idempotent migration that:
  1. Checks for column existence before altering the table (safe to re-run)
  2. Adds `os_version_id INT UNSIGNED DEFAULT NULL` to `operating_systems`
  3. Queries all distinct `(name, version)` pairs and assigns sequential integer IDs
  4. Backfills `os_version_id` for all matching rows

- **`Down_20240130115133`** — No-op rollback; the column is not removed on downgrade

- **`init()`** — Registers both migration functions with `MigrationClient`

## Usage Example

```go
// Registered automatically via init(); triggered by the migration runner.
// Manual invocation during testing:
err := Up_20240130115133(tx)

    log.Fatalf("migration failed: %v", err)

```

## Notes

- **Idempotency**: the migration skips the `ALTER TABLE` if `os_version_id` already exists, preventing duplicate-column errors on repeated runs.
- **ID assignment**: IDs are positional (`id+1`) based on the order returned by `SELECT DISTINCT` — the assignment is **not deterministic** across different MySQL versions or table states. This should be considered when relying on specific ID values.
- The down migration is intentionally empty; reverting requires a manual `ALTER TABLE operating_systems DROP COLUMN os_version_id`.
