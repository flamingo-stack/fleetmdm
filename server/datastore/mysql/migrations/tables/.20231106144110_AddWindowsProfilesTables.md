Database migration that renames Apple MDM enum tables to generic names and creates two new tables for Windows MDM configuration profile management.

## Key Components

- **`Up_20231106144110`** — Applies the migration in three steps:
  1. Renames `mdm_apple_delivery_status` → `mdm_delivery_status` (shared by Apple and Windows)
  2. Renames `mdm_apple_operation_types` → `mdm_operation_types` (shared by Apple and Windows)
  3. Creates `mdm_windows_configuration_profiles` — stores desired profile state per team
  4. Creates `host_mdm_windows_profiles` — tracks per-host profile delivery status
- **`Down_20231106144110`** — No-op; rollback is not implemented
- **`init`** — Registers both functions with `MigrationClient`

## Table Schema Summary

| Table | Purpose |
|---|---|
| `mdm_windows_configuration_profiles` | Desired Windows MDM profiles per team (name, SyncML payload) |
| `host_mdm_windows_profiles` | Per-host profile delivery state (status, operation type, retries) |

## Usage Example

This migration is applied automatically by the Fleet migration runner. To run manually:

```go
// Executed via the migration client, not called directly.
// To apply all pending migrations:
migrationClient.Up(db)

// Individual function signature (for reference):
func Up_20231106144110(tx *sql.Tx) error
```

## Notes

- The table renames make `mdm_delivery_status` and `mdm_operation_types` platform-agnostic, shared between Apple and Windows MDM flows.
- `host_mdm_windows_profiles` intentionally has **no FK** on `profile_id` — hosts may retain profile records after a profile is deleted from the configuration table.
- SyncML payloads are stored as `MEDIUMBLOB` supporting up to ~16 MB.
