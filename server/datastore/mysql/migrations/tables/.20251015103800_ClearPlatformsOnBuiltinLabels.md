Database migration that clears the `platform` field on all built-in labels, ensuring consistent label state across Fleet environments regardless of initial deployment version.

## Key Components

- **`Up_20251015103800`** — Sets `platform = ''` for all rows where `label_type = LabelTypeBuiltIn`, using a fixed timestamp (`2025-10-09`) to keep generated schema output deterministic
- **`Down_20251015103800`** — No-op rollback; the clearing operation is not reversible by design
- **`init`** — Registers the migration pair with `MigrationClient`

## Background

This migration resolves a state divergence between Fleet environments caused by the ordering of `tables` vs. `data` migrations. Previously, platform clearing for built-in labels only happened in a `data` migration (`20210330130314_UpdateBuiltinLabels.go`). Because `data` migrations are deprecated and run after `tables` migrations, environments that deployed Fleet at different versions could end up with different `platform` values on built-in labels.

Moving the logic into a `tables` migration guarantees all environments converge to the same state.

## Why Clear Platforms on Built-in Labels?

- **Dynamic labels** — An empty `platform` ensures label queries run on all hosts, preventing stale membership (e.g., a host dual-booted from Ubuntu to Windows retaining a Linux label)
- **Manual labels** — `platform` serves no functional purpose for built-in manual labels
- **Idempotent** — Safe to re-run; repeated execution produces the same result

## Usage Example

```go
// Applied automatically by the migration runner on startup.
// To run manually during development:
fleet db migrate --env tables
```

```go
// The core SQL executed:
sql := "UPDATE labels SET platform = '', updated_at = ? WHERE label_type = ?"
tx.Exec(sql, updatedAt, fleet.LabelTypeBuiltIn)
```
