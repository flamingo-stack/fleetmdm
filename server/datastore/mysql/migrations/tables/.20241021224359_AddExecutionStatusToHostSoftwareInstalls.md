Database migration that adds a virtual `execution_status` computed column to the `host_software_installs` table, deriving install/uninstall state from existing exit code columns.

## Key Components

- **`Up_20241021224359`** — Idempotent migration that adds a `VIRTUAL` generated `execution_status` ENUM column derived from script exit codes and host assignment flags
- **`Down_20241021224359`** — No-op rollback (column addition is considered safe to leave)
- **`init`** — Registers both migration functions with `MigrationClient`

## Column Logic

The `execution_status` ENUM resolves via a `CASE` expression evaluated in priority order:

| Condition | Status |
|---|---|
| `post_install_script_exit_code = 0` | `installed` |
| `post_install_script_exit_code != 0` | `failed_install` |
| `install_script_exit_code = 0` | `installed` |
| `install_script_exit_code != 0` | `failed_install` |
| `pre_install_query_output = ''` | `failed_install` |
| `host_id IS NOT NULL` and `uninstall = 0` | `pending_install` |
| `uninstall_script_exit_code != 0` | `failed_uninstall` |
| `uninstall_script_exit_code = 0` | `NULL` (available for reinstall) |
| `host_id IS NOT NULL` and `uninstall = 1` | `pending_uninstall` |
| Default | `NULL` |

> **Note:** This column tracks per-record execution state regardless of the `removed` flag. The existing `status` column remains for aggregate host-count metrics and is reset when installers change.
