Database migration that introduces a staging table for Windows MDM configuration profiles awaiting asynchronous deletion, and adds a supporting index to improve lookup performance during garbage collection.

## Key Components

- **`Up_20260611202649`** — Creates `mdm_windows_configuration_profiles_pending_delete` and conditionally adds a secondary index on `host_mdm_windows_profiles.profile_uuid`
- **`Down_20260611202649`** — No-op rollback (intentionally empty)
- **`init`** — Registers both migration functions with `MigrationClient`

## Schema Changes

**New table: `mdm_windows_configuration_profiles_pending_delete`**

| Column | Type | Purpose |
|---|---|---|
| `profile_uuid` | `VARCHAR(37)` PK | Identifies the deleted profile |
| `team_id` | `INT UNSIGNED` | Team scope |
| `name` | `VARCHAR(255)` | Profile name |
| `syncml` | `MEDIUMBLOB` | SyncML payload needed to generate `<Delete>` commands |
| `created_at` | `DATETIME(6)` | Insertion timestamp |

**New index: `idx_host_mdm_windows_profiles_profile_uuid`** on `host_mdm_windows_profiles(profile_uuid)`

## Design Rationale

- **Separate table vs. soft delete** — A `deleted_at` column on `mdm_windows_configuration_profiles` would violate `UNIQUE(team_id, name)`, blocking re-creation of same-named profiles while stale rows linger.
- **Async O(profiles) deletes** — The profile-manager cron processes removals in bounded 2,000-host batches, matching the existing team-transfer pattern and preventing large-removal timeouts.
- **Reference-counted GC** — Rows are removed once no `host_mdm_windows_profiles` row still references the `profile_uuid`, ensuring offline hosts receive their `<Delete>` command on reconnect.
- **Idempotent** — Uses `CREATE TABLE IF NOT EXISTS` and `indexExistsTx` guards so re-running is safe.
