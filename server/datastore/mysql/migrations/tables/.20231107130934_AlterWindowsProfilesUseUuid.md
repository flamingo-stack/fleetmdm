Database migration that transitions Windows MDM profile tables from integer-based `profile_id` primary keys to UUID-based `profile_uuid` primary keys, with idempotency checks to safely handle re-execution.

## Key Components

- **`Up_20231107130934`** — Idempotent forward migration that:
  1. Checks if migration has already been applied via `INFORMATION_SCHEMA.STATISTICS`
  2. Drops `AUTO_INCREMENT` and the existing `PRIMARY KEY` on `mdm_windows_configuration_profiles`
  3. Adds `profile_uuid VARCHAR(36)` to both `mdm_windows_configuration_profiles` and `host_mdm_windows_profiles`
  4. Generates UUIDs using MySQL's `uuid()` function for all existing profile rows
  5. Propagates UUIDs to `host_mdm_windows_profiles` via a correlated subquery, falling back to a new `uuid()` if no match exists
  6. Sets `profile_uuid` as the new primary key and drops the old `profile_id` column from both tables

- **`Down_20231107130934`** — No-op rollback (intentionally irreversible)

- **`columnExists`** — Helper (defined elsewhere) used to guard column additions, ensuring the migration is safe to re-run

## Usage Example

This migration is registered automatically via `init()` and executed by the migration client:

```go
// Registered automatically on package import
func init() {
    MigrationClient.AddMigration(Up_20231107130934, Down_20231107130934)
}

// Executed by the migration runner
err := MigrationClient.Up(db)
if err != nil {
    log.Fatalf("migration failed: %v", err)
}
```

## Notes

- **MySQL 5.7 compatibility:** `uuid()` cannot be used as a column `DEFAULT`, so UUIDs are populated via `UPDATE` statements after column creation.
- The composite primary key on `host_mdm_windows_profiles` becomes `(host_uuid, profile_uuid)`.
