Records a new activity, fires optional webhook notifications, and handles next upcoming activity activation.

## Key Components

| Symbol | Description |
|--------|-------------|
| `webhookPayload` | JSON struct sent to the activity webhook endpoint, containing timestamp, actor info, activity type, and raw details |
| `NewActivity` | Marshals activity details, triggers webhook delivery, optionally activates the next upcoming activity, then persists the record via the store |
| `fireActivityWebhook` | Asynchronously POSTs the webhook payload to a configured URL using exponential backoff (max 30 minutes); retries only on HTTP 429 responses |

## Usage Example

```go
svc := &Service{store: store, providers: providers, logger: logger}

// Create activity with an authenticated user
err := svc.NewActivity(ctx, &api.User{
    ID:    42,
    Name:  "Alice",
    Email: "alice@example.com",
}, &MyActivityDetails{HostID: 7})

// Create automation-triggered activity (no user)
err = svc.NewActivity(ctx, nil, &AutomatedInstallActivity{FromAutomation: true})
```

## Notes

- **Webhook delivery** is fire-and-forget (goroutine), keeping the main request path non-blocking.
- **Retry logic**: only HTTP `429 Too Many Requests` is retried; all other errors are treated as permanent failures via `backoff.Permanent`.
- **Tracing**: the async goroutine creates a new root OTel span linked to the originating request span, enabling cross-boundary trace correlation.
- **Alias duplication**: JSON field aliases defined via `eu.ExtractAliasRules` are duplicated in stored details for backward compatibility (e.g. `team_id` ↔ `fleet_id`).
- **Deleted users**: a non-zero `user.Deleted` flag suppresses the `actor_id` field in the webhook payload while still preserving `actor_full_name` and `actor_email`.
