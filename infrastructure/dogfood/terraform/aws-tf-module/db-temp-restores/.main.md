Terraform configuration for provisioning temporary Aurora MySQL database restores from snapshots in the Fleet dogfood AWS environment, with VPN-restricted developer access.

## Key Components

| Resource / Block | Purpose |
|---|---|
| `backend "s3"` | Remote state stored in S3 with DynamoDB locking, encrypted via KMS |
| `terraform_remote_state.dogfood` | Reads shared VPC outputs (subnets, VPC ID) from the dogfood remote state |
| `aws_security_group.db_restore_vpn_access` | Security group restricting MySQL (port 3306) ingress to three VPN subnets |
| `aws_db_subnet_group.shared` | Subnet group scoped to the shared dogfood database subnets |
| `module.dev_restore_dbs` | Aurora Serverless v2 MySQL cluster restored from a customer snapshot per entry in `local.customers` |
| `aws_secretsmanager_secret_version.aurora_master` | Retrieves the auto-managed master credentials for each restored cluster |
| `module.mysql_dev_access` | Child module (`./mysql_dev_access`) that provisions per-developer MySQL users against each restored cluster |

**Key locals:**

- `allowed_subnets` — three `/24` VPN CIDR blocks permitted to reach MySQL
- `developers` — list of developer usernames granted access
- `local.customers` — map of restore target name → RDS snapshot ARN (drive all `for_each` loops)

## Usage Example

Add or update a snapshot restore by editing `local.customers`:

```bash
# 1. Add a new entry to local.customers in main.tf
customers = {
  fleet-dogfood-1 = "arn:aws:rds:us-east-2:160035666661:cluster-snapshot:rds:fleet-dogfood-1-2026-05-07-02-06"
  fleet-dogfood-2 = "arn:aws:rds:us-east-2:160035666661:cluster-snapshot:rds:fleet-dogfood-2-2026-05-08-02-06"
}

# 2. Plan and apply
terraform init
terraform workspace select dogfood
terraform plan
terraform apply
```

Outputs (`databases`, `developer_passwords`) are marked `sensitive = true` and must be retrieved explicitly:

```bash
terraform output -json developer_passwords
```

## Notes

- Clusters use **Aurora Serverless v2** (`db.serverless`) scaling between 0–4 ACUs to minimise cost
- `deletion_protection = false` and `skip_final_snapshot = true` reflect the ephemeral, restore-only nature of these clusters
- Master credentials are managed by AWS Secrets Manager automatically via `manage_master_user_password = true`
