Terraform configuration for enrolling AWS member accounts into GuardDuty threat detection under a centralized security account, using a multi-provider pattern to manage cross-account IAM role assumptions.

## Key Components

| Component | Description |
|-----------|-------------|
| `backend "s3"` | Remote state stored in S3 with DynamoDB locking and KMS encryption |
| `provider "aws" (security)` | Assumes admin role in the central security account (`353365949058`) |
| `provider "aws" (member)` | Assumes admin role in the target member account (resolved from workspace) |
| `provider "aws" (root)` | Uses default credentials to query AWS Organizations |
| `locals` | Parses `terraform.workspace` (format: `account_id:region`) to extract `account_id` and `region` |
| `aws_guardduty_member` | Invites the member account into the security account's GuardDuty detector |
| `aws_guardduty_detector` | Enables GuardDuty on the member account side |

## Usage Example

Each member account is managed as a separate Terraform workspace. The workspace name encodes both the AWS account ID and region:

```bash
# Initialize and select a workspace for a specific member account
terraform init
terraform workspace new 123456789012:us-east-2

# Plan and apply for that member account
terraform plan
terraform apply
```

The workspace value (`123456789012:us-east-2`) is split by `locals` to derive:
- `local.account_id` → `123456789012`
- `local.region` → `us-east-2`

## Notes

- The `email` field on `aws_guardduty_member` has `ignore_changes` set since GuardDuty does not allow email updates after invitation.
- `disable_email_notification = true` suppresses the default AWS invitation email to member accounts.
- State key should follow the pattern `account_alias/unique_key/terraform.tfstate` per inline comments.
