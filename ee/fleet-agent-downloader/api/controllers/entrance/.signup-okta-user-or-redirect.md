Handles Okta SSO user provisioning by looking up or creating a Fleet MDM user record from the Okta session, then attaches the resolved database ID to the session before redirecting.

## Key Components

- **`oktaClientSecret` guard** — Redirects to `/login` if Okta SSO is not configured
- **Session validation** — Validates the presence of `req.session.passport.user` before proceeding
- **User lookup** — Queries the `User` model by `preferred_username` (email) from Okta's `userinfo`
- **User provisioning** — Creates a new user record if no existing match is found, using `given_name`, `family_name`, and `sub` as the hashed password seed
- **Session binding** — Sets `req.session.userId` to the resolved database record ID
- **`redirect` exit** — Falls through to `/` on success; falls back to `/login` on any guard failure

## Usage Example

This action is invoked as the Okta OAuth2 callback handler in `config/routes.js` or via Passport middleware:

```javascript
// config/routes.js
'GET /auth/okta/callback': { action: 'signup-okta-user-or-redirect' }
```

On a successful Okta authentication, the Passport strategy populates `req.session.passport.user.userinfo`. This action then resolves or provisions the local user:

```javascript
// Resulting session state after successful execution
req.session.userId = 42; // local DB id, matched or newly created
// User is redirected to '/'
```

> **Note:** Passwords for Okta-provisioned accounts are hashed from the Okta `sub` claim and **cannot be changed** through the standard password reset flow.
