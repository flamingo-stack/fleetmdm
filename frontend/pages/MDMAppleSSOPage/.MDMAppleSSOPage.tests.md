Test suite for the `MDMAppleSSOPage` (DEP SSO Login) component, validating SSO API call behavior across different MDM enrollment initiator scenarios.

## Key Components

- **`DEPSSOLoginPage`** — The component under test, rendered via `createCustomRenderer` with a backend mock
- **`createMockLocation`** — Helper factory that produces a typed `HistoryLocation<IMDMSSOParams>` with configurable `pathname`, `query`, and other fields
- **`mdmSSOUrl`** — Intercept target at `POST /mdm/sso` via MSW

## Test Cases

| Test | Behavior Verified |
|------|-------------------|
| `mdm_sso` initiator in query | Auto-triggers SSO API call with correct `initiator` + `deviceinfo` |
| `setup_experience` initiator | Skips auto-redirect; renders manual "Sign in" button instead |
| No initiator provided | Falls back to `mdm_sso` as default initiator |
| `account_driven_enroll` pathname | Sends `account_driven_enroll` as initiator |
| `account_driven_enroll` with token | Sends `account_driven_enroll:testtoken` as compound initiator |

## Usage Example

```typescript
// Example: how the component is rendered in tests
render(
  <DEPSSOLoginPage
    location={createMockLocation({
      pathname: "/mdm/sso",
      query: { initiator: "mdm_sso", deviceinfo: "testdeviceinfo" },
    })}
    params={{}}
    router={createMockRouter()}
    routes={[]}
  />
);

// Assert the SSO API received the correct payload
await waitFor(() => {
  expect(requestBody.initiator).toBe("mdm_sso");
});
```

## Notes

- Uses **MSW** (`http.post`) to intercept and capture request bodies without real network calls
- The `setup_experience` flow is the only initiator that suppresses auto-redirect in favor of user-initiated sign-in
- Token-based `account_driven_enroll` uses a colon-delimited format: `account_driven_enroll:<token>`
