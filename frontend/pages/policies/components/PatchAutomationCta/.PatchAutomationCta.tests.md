Unit tests for the `PatchAutomationCta` component, verifying rendering behaviour, display name resolution, and user interaction across various policy states.

## Key Components

### `createMockPatchPolicy(overrides?)`
Factory function returning a fully typed `IPolicy` object with sensible defaults for a macOS patch policy (`type: "patch"`, `patch_software` set to Zoom). Accepts partial overrides for targeted test scenarios.

### `renderWithAppContext(ui)`
Helper that wraps a React element with `AppContext.Provider` (seeded from `initialState` and `createMockConfig()`), satisfying the `useGitOpsMode` hook consumed by `GitOpsModeTooltipWrapper` inside the component.

### Test Suites

**"renders when conditions are met"**
- Shows the CTA card and `Add automation` button when `canEditPolicy` is `true`.
- Prefers `patch_software.display_name` over `patch_software.name` in the label.
- Falls back to normalised well-known names when `display_name` is absent (e.g. `Microsoft.CompanyPortal` → `Company Portal`).
- Fires `onAddAutomation` on button click.
- Hides the CTA entirely when `canEditPolicy` is `false`.
- Shows `"Adding..."` text and removes the button while `isAddingAutomation` is `true`.

**"renders nothing when conditions are not met"**
- Non-patch (`type: "dynamic"`) policies produce no output.
- Missing `patch_software` suppresses the CTA.
- A no-team policy (`team_id === 0`) still renders the CTA correctly.
- Policies already carrying `install_software` suppress the CTA.

## Usage Example

```typescript
// Snapshot of a passing render test
it("shows Add automation button for a patch policy", () => {
  renderWithAppContext(
    <PatchAutomationCta
      storedPolicy={createMockPatchPolicy()}
      canEditPolicy
      onAddAutomation={jest.fn()}
    />
  );
  expect(screen.getByText(/Automatically patch Zoom/)).toBeInTheDocument();
  expect(screen.getByRole("button", { name: /Add automation/ })).toBeInTheDocument();
});
```
