Brief overview of the test file's purpose: Renders and validates UI states of the `HostSoftwareLibraryTable` component across different user permissions, data conditions, and platform configurations.

## Key Components

| Export / Symbol | Purpose |
|---|---|
| `describe("HostSoftwareLibraryTable")` | Top-level test suite for the component |
| `baseProps` | Shared default prop set reused across all test cases |
| `renderWithContext` | Helper wrapping `createCustomRenderer` with a global admin app context |
| `createMockGetHostSoftwareResponse` | Mock factory generating host software API response shapes |
| `createMockRouter` / `mockRouter` | Stub router injected into the component |

## Test Cases

| Test | Assertion focus |
|---|---|
| Truly empty state — user **can** add software | Empty state copy, "Add software" CTA button, `0 items` count, search input disabled |
| Truly empty state — user **lacks** permission | Permission-aware copy, no "Add software" button rendered |
| Filtered empty state (search active) | Search input remains **enabled** when a `searchQuery` is present |
| Android platform guard | Renders "installers are not supported for this host" fallback message |

## Usage Example

```typescript
// Run all tests in this file
// From the repository root:
// npx jest HostSoftwareLibraryTable.tests.tsx

// Add a new test case following the existing pattern:
it("renders loading state", () => {
  renderWithContext({ isLoading: true });
  expect(screen.getByRole("progressbar")).toBeInTheDocument();
});
```

## Notes

- The **Android unsupported state** is intentionally tested at the table level as a defensive fallback, even though the parent `HostDetailsPage` also guards it.
- `renderWithContext` defaults to a **global admin** user (`isGlobalAdmin: true`). Override `context` inside the helper if testing non-admin scenarios.
