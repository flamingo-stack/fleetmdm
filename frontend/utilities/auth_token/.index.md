Utility module for managing user authentication tokens via browser cookies, with automatic handling of secure (`__Host-` prefixed) vs. non-secure cookie names based on the current protocol context.

## Key Components

| Export | Type | Description |
|--------|------|-------------|
| `save` | `(token: string, expiresAt?: Date) => void` | Persists the auth token as a cookie; defaults to 5-day expiration |
| `get` | `() => string \| null` | Retrieves the stored auth token, or `null` if absent |
| `remove` | `() => void` | Deletes the auth token cookie, matching secure/sameSite attributes |

### Internal Helpers

- **`isSecure()`** — Returns `true` when the page is served over HTTPS.
- **`getTokenName()`** — Returns `__Host-token` on HTTPS (enforcing host-binding via the `__Host-` prefix) or `token` on plain HTTP, ensuring get/set/remove always target the same cookie name.

## Usage Example

```typescript
import authToken from "./authToken";

// Save a token after login (optional custom expiry)
authToken.save("eyJhbGciOiJIUzI1NiJ9...");

// Save with a specific expiration date
const expiry = new Date("2025-12-31");
authToken.save("eyJhbGciOiJIUzI1NiJ9...", expiry);

// Read the token for API requests
const token = authToken.get();
if (token) {
  headers["Authorization"] = `Bearer ${token}`;
}

// Clear the token on logout
authToken.remove();
```

## Notes

- On **HTTP** deployments (e.g. Docker without TLS), the `__Host-` prefix and `Secure` attribute are silently rejected by browsers, so a plain `token` cookie name is used as a fallback.
- All cookies use `sameSite: "lax"` to balance CSRF protection with usability.
- The `secure` and `sameSite` options are included in `remove()` to ensure the browser correctly identifies and deletes the cookie.
